# Arlt HiFi Player Design Language

## 核心方向

Arlt HiFi Player 的基础设计语言应接近安静、克制、稳定的桌面音乐工具：清晰的信息层级、低噪声界面、稳定控件尺寸和可预测交互。产品当前定位是本地 HiFi 桌面播放器，不是营销页、游戏界面或视觉舞台应用。

主播放器页面不保留右侧舞台、角色舞台或动态视觉舞台。任何未来视觉增强都必须服务播放状态、专辑内容或桌面伴随模式，并且可以关闭。

## 设计原则

- 系统优先：播放器首先是一个可靠的桌面音乐应用。
- 本地优先：音乐库、播放队列、播放栏和 HiFi 信息是第一层体验。
- 克制表达：避免高饱和霓虹、游戏 HUD、发光按钮和复杂装饰边框。
- 平滑稳定：动效用于反馈、过渡和状态确认，而不是装饰。
- 操作不被遮挡：任何视觉反馈都不能遮挡播放控制、音乐库列表、菜单或设置。
- 主题不改规则：主题可以改变色彩和内容资产，不能改变基础交互模型。

## 1. 系统 UI 层

系统 UI 层是产品的基础，必须清晰、低噪声、可预测。

### 包含范围

- 导航栏
- 音乐库列表
- 播放队列
- 播放栏
- 按钮
- 滑杆
- 菜单
- 弹窗
- 设置页
- HiFi 信息面板

### 视觉要求

- 使用半透明或低噪声 surface。
- 使用柔和阴影和低对比边框。
- 文本层级清晰，不依赖强烈色彩制造重点。
- 控件尺寸稳定，hover、tap、focus 不造成布局跳动。
- 列表内容必须支持长标题、长路径和未知元数据，不溢出、不重叠。

### 交互要求

- 页面切换、面板展开、列表更新应平滑自然。
- hover/tap 反馈应轻，不做炫技式动画。
- 弹窗、菜单、滑杆、tabs 等复杂交互优先使用接近原生行为的组件。
- 文件选择、扫描、播放错误需要有明确状态反馈。

## 2. 播放与音乐库层

播放与音乐库层是当前产品核心。

### 必须优先保证

- 音乐库扫描状态：空、扫描中、成功、失败。
- 列表字段：标题、艺术家、专辑、时长、音质信息。
- 播放状态：播放、暂停、切歌、进度、时长、错误。
- HiFi 信息：在真实接入前明确 mock 或未知状态。

### 限制

- 不为了视觉装饰牺牲列表密度和可读性。
- 不在主页面添加固定右侧舞台。
- 不将未来 companion 或视觉反馈作为当前 UI 骨架。

## 3. 轻量视觉反馈层

轻量视觉反馈可以增强播放体验，但必须是可选增强。

### 适合的位置

- 播放栏状态反馈。
- 封面或专辑视觉区域。
- 列表当前播放行高亮。
- 可关闭的小窗口或桌面伴随模式。
- 主题色和微交互反馈。

### 限制

- 不做过度弹跳、闪烁、爆炸粒子。
- 不用动效吸引用户离开核心任务。
- 不让反馈覆盖按钮、滑杆、列表和菜单。
- 不把音乐播放器变成游戏界面或视觉舞台应用。

## 4. 主题资产层

主题资产层管理可替换资源，包括色彩 token、专辑视觉、微交互动效和可选视觉反馈资源。

### 资产类型

- 系统 token 与内容 token。
- 专辑视觉资源。
- 背景柔和纹理或低干扰视觉素材。
- 微交互动效资源。
- 可选桌面伴随模式资源。

### 约束

- 主题不能改变基础导航结构。
- 主题不能改变按钮、菜单、弹窗、滑杆的基础交互规则。
- 主题不能降低可读性。
- 主题不能加入固定右侧舞台、角色舞台或动态视觉舞台。

## 禁止项

- 高饱和霓虹风。
- 游戏 HUD。
- 发光按钮。
- 复杂装饰边框。
- 视觉元素遮挡核心操作。
- 过度动效。
- 主题改变基础交互规则。
- 主播放器页面出现右侧舞台、角色舞台或动态视觉舞台。

## 技术建议

- CSS Variables：管理系统 token 与主题 token。
- Tailwind CSS：负责布局和基础样式。
- Zustand：管理音乐库、播放队列和播放状态。
- HTMLAudioElement：当前真实播放 MVP。
- 后续可评估 Rust audio-core：负责解码、输出设备和 HiFi 链路。
- Rive / Lottie：仅用于轻量微交互或非核心视觉反馈。

## 判断标准

当一个设计方案出现视觉增强时，应先问：

- 它是否影响了导航、播放控制或列表阅读？
- 它是否让系统控件变得像游戏 UI？
- 它是否只是装饰，而没有服务播放状态或音乐内容？
- 它是否可以关闭或替换，而不影响基础交互？

如果答案显示它正在破坏系统 UI 层，应退回到桌面音乐播放器的基础规则。
