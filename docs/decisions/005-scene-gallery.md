# ADR 005: 以实时 3D 收藏场景作为库与播放的核心视图

## 状态

已接受（2026-10-24），修订 [ADR 004](004-visual-direction.md) 的部分视觉结论，并改写 AGENTS.md / CLAUDE.md 中"禁止动态视觉舞台"的措辞。

## 背景

原约束「主播放器不得出现右侧舞台、角色舞台、Live2D、MV 或动态视觉舞台」的**目的是防止播放器变成游戏 HUD 或角色看板**：即视觉装饰与音乐内容无关、抢占注意力、遮挡操作。

产品负责人提出新的界面方向：

> 做一个类似实时渲染的场景，场景中放着用户收藏歌曲封面的 CD，随着 CD 数量增加，场景产生变化（背景、储存装置变化）；点击 CD 后有过渡动画跳转到播放 CD 的界面；播放界面的 CD 悬浮、随鼠标倾斜、播放时转动。

这不是"装饰舞台"，而是**把曲库本身空间化**：场景即内容、即导航。原约束的字面表述会误伤这个方向，因此需要显式修订，而不是绕过。

## 决策

### 1. 约束重新表述（取代原单条禁令）

**禁止**（不变，目的不变）：

- 装饰性右侧舞台、角色立绘、看板娘、Live2D。
- MV、视频背景、外部视频素材驱动的背景。
- 与音乐库内容无关的满屏粒子/闪烁/游戏 HUD 式数值面板。
- 遮挡播放控制、进度、错误提示与列表阅读的视觉层。
- 不可关闭的动效。

**允许**（新）：

- 以**收藏曲目本身**为唯一内容源的 3D 场景层：CD 的陈列装置、播放台、镜头运动。
- 场景内的环境动效（尘埃、扫光、灯光呼吸），仅在「丰富」动效档启用，且必须可关闭。
- 场景与系统层（列表、队列、设置、播放控制）并存：场景是库的一种视图，不是唯一入口。

判定标准（写进评审清单）：**每个 3D 元素是否对应一张真实的收藏 CD 或一个真实的播放状态？** 若不能对应，即为装饰，应删除。

### 2. 场景层的定位

| 层 | 内容 | 角色 |
| --- | --- | --- |
| 场景层（新增） | 3D 展厅、CD 陈列装置、播放台悬浮 CD | 库的主视图 + 播放的主视觉 |
| 系统层（保留） | 列表视图、队列、设置、播放控制、错误提示、信号信息 | 操作与信息，永不被场景遮挡 |
| 背景层（降级） | 静态壁纸 | 场景不可用时的兜底 |

列表视图（当前 S2 已实现）**不废弃**，它同时承担三个职责：无障碍路径、WebGL 降级路径、大曲库检索路径。

### 3. 技术选型

- `three.js` + `@react-three/fiber`（React 18 兼容线 8.x）+ `@react-three/drei`（按需引入，避免整包）。
- 只在渲染层使用，通过 `React.lazy` 懒加载，不阻塞系统层首帧。
- 不使用物理引擎（无需 cannon/rapier）：CD 的倾倒与落位用插值动画表达，避免为视觉引入刚体模拟。
- 封面纹理走既有受控媒体协议（`arlt-hifi-media://image/...`），不新增文件访问能力。

### 4. 数据驱动

场景形态由**曲库数量**决定（每 24 首增长一个展示段 Bay），收藏只改变 CD 外观（金边 + 边缘微光），不影响空间。

阈值与空间映射写成纯函数并单测（`getGalleryAnchor` / `getBayCount`），不散落在组件里。

### 5. 性能与可达性是一等约束

- 目标：1280×820 窗口 ≥ 45–50fps（集显），静止时零渲染（`frameloop="demand"`）。
- 连续低帧率（< 30fps 持续 3 秒）自动降级为静态场景 + 列表。
- 键盘与读屏必须能完成「浏览曲库 → 打开曲目 → 播放控制」全流程。

细节见 [场景展厅规格](../product/scene-gallery.md)。

## 影响

- 新增依赖：three / @react-three/fiber / @react-three/drei，预计 bundle +150–200KB gzip；桌面端可接受，需在 S7 校验冷启动。
- 美术工作量成为最大成本项：长廊装置 + 生长动画 + 播放台 + 转场。
- 封面提取（`music-metadata`）从"提升项"变成**关键路径**：没有封面的 CD 会直接破坏场景可信度。
- 阶段计划新增 S2R 系列（S2R-0 至 S2R-5），原 S3–S8 顺延，见 [roadmap](../product/roadmap.md)。
- AGENTS.md / CLAUDE.md 中的硬约束条目同步改写并指向本 ADR。

## 备选方案与否决原因

| 方案 | 否决原因 |
| --- | --- |
| CSS 3D 变换搭一个"架子" | 无光照、无材质层次，做不出"实时渲染场景"的质感；倾斜与反射廉价 |
| 静态插画 + 微动效 | 无法随曲库数量延伸空间，核心需求不成立 |
| PixiJS / 2D 画布 | 本质是 2D，无法实现镜头、景深与悬浮 CD |
| 引入物理引擎 | 为纯视觉引入刚体模拟，成本与不稳定性不划算 |
| 固定"六档房间替换" | 被第二轮需求否决：用户要的是一条连续延伸的长廊，而不是换房间 |

## 风险

| 风险 | 应对 |
| --- | --- |
| Windows 集显/驱动导致帧率不达标 | S2R-0 先用 60 张 CD 的走廊做性能 spike，不达标就砍效果（景深/阴影）而不砍长廊 |
| 写实风格成本失控 | 写实指"光照与材质可信"，不做照片级；环境光程序化生成，不引入 HDRI/贴图资产 |
| 长曲库显存失控 | Bay 虚拟化 + 纹理 LRU + 实例化，常驻 Bay ≤ 5 |
| 长距离镜头移动晕眩 | 跨 Bay 用两段式（淡出→滑行入场），限制俯仰角 |
| 无障碍被牺牲 | 列表视图与 ARIA 播报列为门禁项，不是"后续优化" |
| 工期显著延长 | S2R 是最大单项，按 6 个子阶段交付，每阶段可暂停 |

## 修订记录

- 2026-10-24 第二轮（产品负责人确认）：曲库**全部**入场；收藏只改变外观（金边）；风格改为**偏写实**；空间模型由"六档房间替换"改为"连续 CD 长廊 + 按 Bay 生长 + 镜头沿走廊移动"；成长改由曲库数量驱动。规格见 [CD 长廊](../product/scene-gallery.md)。
